## Isolation and migration lifecycle

The runner accepts no database URL. It discards inherited database/libpq/JWT
configuration in its subprocess, rejects remote Docker contexts, and generates
unique container/database/role names and independent random passwords. The image
is pinned as:

`postgres:17.6-bookworm@sha256:f3bd19c606e442c3d7bdfa8002e03fe260a1023351e0ea4598032022b68dd6e3`

Only a dynamically allocated 127.0.0.1 port is published. The data directory uses
tmpfs, overriding the image's default volume; no persistent volume is mounted.
Ownership checks require full ID, exact name, random label, expected port and
storage. Database identity is checked before DDL. Migration and runtime roles
are separate; runtime cannot create tables or databases and is not a superuser.

Alembic runs the existing reviewed revision with its explicit opt-in flag, using
only the generated migration URL. The runner verifies users and alembic_version,
runs integration tests, downgrades to base, verifies users is gone, then upgrades
again and verifies an empty table at head. No development/production migration
was executed. finally removes only the captured, revalidated container ID.

## Limitations and next step

Forced process termination or loss of the Docker daemon can prevent finally cleanup;
the test-environment document gives ownership-checked recovery instructions. tmpfs
does not guarantee forensic erasure from host swap. The pinned PostgreSQL image is
a reproducible test baseline, not a production patch policy. Registry access is
required for pulls. Default CI remains Docker-free; an integration CI job is follow-up.

Review this checkpoint before proceeding. The next authentication checkpoint can
build hashing and registration/login on the validated persistence foundation,
following the approved plan. The separate versioned 500/429 contract proposal
remains unresolved; existing v1 wire contracts are unchanged.
